Context

MailCheck is an email-verification SaaS — it tells customers whether an email address is valid and deliverable before they send to it. The product is a Ruby on Rails application backed by PostgreSQL.

This one runs on EC2 with AWS CodeDeploy and an Auto Scaling Group, provisioned by Ansible — the contrast to the containerised ECS Fargate services I built elsewhere. See the side-by-side writeup: EC2 vs ECS.

The problem

The verification API has to stay up as traffic rises and falls, and new releases need to ship without taking the service offline. Running Rails on a single hand-configured EC2 box makes both of those hard: scaling means setting up another server by hand, and shipping means logging into a live machine to update code.

I needed capacity that grows and shrinks on its own and a release path that doesn't depend on anyone touching a running instance — where every server, whether it has been running for a while or only just launched, is configured the same way and runs the current revision.

Architecture

What I built

Compute

  • An EC2 Auto Scaling Group running the Rails application across two or more instances, so capacity can grow and shrink without manual server setup.
  • Every instance in the group is interchangeable: a newly launched instance comes up configured and running the current release, with no hand steps.

Config / provisioning

  • Ansible playbooks that provision each instance — installing and configuring the Rails application runtime and PostgreSQL.
  • Provisioning lives in code, so instances are reproducible and don't drift apart from one another over time.

CI/CD

  • A Bitbucket pipeline that builds the release on every push to the deploy branch.
  • AWS CodeDeploy as the single path to production, rolling each release onto the Auto Scaling Group with minimal downtime.

Data

  • PostgreSQL as the application database, provisioned alongside the app by Ansible.

Deploy flow

  1. git push — a developer pushes to the deploy branch.
  2. Bitbucket pipeline builds — the pipeline runs and produces the release to be deployed.
  3. CodeDeploy deploys to the Auto Scaling Group — AWS CodeDeploy rolls the new revision out across the instances in the group, with minimal downtime.
  4. Instances converge on the current revision — running instances take the new release, and any instance the group launches later comes up on the current revision automatically.

Security decisions

Deploys only through the pipeline

CodeDeploy is the single path to production — releases don't go out by someone SSHing into a live box to edit code. What's running is always a built, known revision.

Instance config in code

Ansible describes the runtime and configuration, so instances are provisioned the same way every time rather than hand-tuned. That keeps the fleet consistent and makes a replacement instance reproducible rather than a snowflake.

Scaling preserves the current release

Instances launched by the Auto Scaling Group pick up the current revision automatically, so scaling out never quietly serves a stale version of the app.
