AI-assisted mobility-equipment intake platform.

Context

CareIntake is an AI-assisted intake platform for mobility equipment — wheelchairs and related mobility aids. Staff upload patient and equipment photos and complete an intake form; the platform uses AWS AI services to analyze the photos and summarize the submitted form so the record is easier to review.

The problem

CareIntake was a second product that needed the same kind of cloud foundation I had already built for Sentinel: a private, container-based platform on AWS with an automated deploy pipeline. Rather than design the network and delivery from scratch, I treated the Sentinel setup as a reusable ECS blueprint and applied it to CareIntake — then added the piece that makes this product different: an AI layer for the intake flow.

Reusing a proven pattern meant the infrastructure and CI/CD were predictable from day one, so the new work could focus on the Rekognition and Bedrock integration and its permissions rather than on re-deriving a VPC and pipeline.

Architecture

What I built

Network

  • Same blueprint as Sentinel: a VPC with public and private subnets, the ALB in public subnets and all compute and data in private subnets.
  • The security-group chain (Internet → ALB → app → database) follows the same pattern — see the Sentinel write-up for the full chain rather than repeating it here.

Compute

  • ECS Fargate running the CareIntake app behind the ALB, in private subnets — same blueprint as Sentinel.
  • AI integration (the distinctive part): the app service calls Amazon Rekognition to analyze uploaded photos — wheelchair, mobility-equipment and patient photos — during intake.
  • It also calls an Anthropic Claude model on Amazon Bedrock to read the intake form data and produce a summary, so reviewers get a condensed view of each submission.

Data

  • RDS PostgreSQL in private subnets, reachable only from the app's security group — same blueprint as Sentinel.

CI/CD

  • Bitbucket pipeline using OIDC to assume a scoped IAM role, build and push to ECR, and update the ECS service — the same deploy lane as Sentinel.

Security

  • Least-privilege task role: the ECS task role is granted only the specific Rekognition and Bedrock actions the app needs to call — nothing broader.
  • Private subnets for the app and database; the ALB is the only public entry point — same blueprint as Sentinel.
  • Bitbucket authenticates to AWS via OIDC, so no long-lived pipeline credentials are stored.

Deploy flow

  1. git push to the CareIntake repository triggers the Bitbucket pipeline.
  2. The pipeline exchanges an OIDC token for a scoped IAM role — no stored AWS keys.
  3. It builds the container image and pushes it to ECR.
  4. It updates the ECS service, which rolls the new task into the Fargate app with minimal-downtime.

This is the same commit-to-live chain as Sentinel, reused unchanged.

Security decisions

Scope the task role to only the AI actions used

The app calls Rekognition and Bedrock, so the ECS task role grants only those specific actions — not blanket AI access. This keeps the AI layer's blast radius tight even though it is the newest and least-proven part of the system.

Keep compute and data in private subnets

The app service and RDS run in private subnets with the ALB as the only public entry point — the same posture as Sentinel, carried over deliberately rather than relaxed for a new product.

OIDC instead of stored pipeline keys

Bitbucket assumes a scoped role via OIDC for every deploy, so there are no long-lived AWS credentials sitting in the CI configuration.

Challenges & fixes

Applying an existing blueprint cleanly to a new product

The main engineering decision here was to treat the Sentinel infrastructure as a reusable blueprint rather than a one-off. The network, security-group chain and CI/CD pipeline came over as a known-good pattern, which let the effort concentrate on the new AI layer and its least-privilege permissions instead of re-deriving the foundation.

What's next

  • Document the exact Claude model version and the photo storage path for the intake flow.
  • Review whether a cost guardrail should wrap the AI calls, as on Sentinel.
